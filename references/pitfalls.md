# 踩坑记录

按"踩到的顺序"记。写在前面的更常犯。

## 渲染

### 1. macOS 上完整 headless 会在 setViewport 抛 TargetCloseError

`puppeteer.launch({ headless: true })` 在 macOS 上开 `setViewport` 时直接崩。用 `headless: 'shell'` + `--no-sandbox` + 独立的 `--user-data-dir`。

### 2. SVG 内实时颗粒把单帧从 88ms 拖到 253ms

给全屏 `<rect>` 铺一张 512×512 噪点 pattern 再 `mix-blend-mode: overlay`，观感是好的，但每帧多 165ms —— 8000 帧就是多 22 分钟。

挪到 ffmpeg：`-vf noise=alls=6:allf=p`。

### 3. `allf=t+u` 让码率从 0.77 飙到 8.8Mbps

`noise` 滤镜的 `allf=t+u`（逐帧随机图案）会让每帧都不可压缩，42 秒的片子涨到 45MB。
用 `allf=p`（固定图案）——1:1 下肉眼看不出区别，码率 2.24Mbps。

### 4. 不要批量删帧

渲染器是增量渲染（跳过已存在的帧）。用脚本 `rm` 旧帧会触发安全钩子，也没必要。
要重渲就 `--force`，或换个 `frames` 目录。

### 4.5 并行渲染会「渲完了但不退出」

`headless:'shell'` 收尾时 `browser.close()` 偶尔永不返回，node 进程就卡住；`build.py` 的并行分片用 `wait()` 等它，于是一整片挂到超时（表现为帧数早就满了、进度却不动）。

修法（已在 `render.js` 里）：

```js
await Promise.race([browser.close().catch(()=>{}), new Promise(r => setTimeout(r, 6000))]);
fs.rmSync(PROFILE, { recursive: true, force: true });
process.exit(0);
```

配套两点：
- `--user-data-dir` 用 `PID + Date.now()`，别只用 PID。PID 会重用，撞上上次残留的 profile 锁会直接卡在启动。
- 每轮渲完删自己的 profile。否则 `/tmp/kids-chrome-*` 会攒到几十个、每个几十 MB。

## Rough.js 手绘档（七个坑）

### 5. `roughness` 是绝对像素值，不是"强度百分比"

示例里的 `roughness: 1.9` 是给几百像素的小图用的。我们的坐标是千级，`1.9` 完全看不出来，要 5–8（小图元按尺寸衰减）。

### 6. `fillStyle` 默认是 `hachure`（交叉排线）

不显式写 `solid`，所有色块会变成铅笔排线。

### 7. 填色和描边必须分两层

一次调用同时给 `fill` 和 `stroke`，两层抖动量不一致，抖大一点色块就从线里溢出来露出底色。
正确做法：**填色用精确路径（roughness 0），描边单独一条手绘线**，手绘感全在描边。

### 8. 圆角矩形不能塞进 `RC.path()`

把 `A` 弧写进 path 交给 Rough.js，弧会被近似得很糟——标签卡边框直接甩成一道大弧压在文字上。
改成沿圆角采样成多边形走 `RC.polygon`。

### 9. 渐变填充不能进 rough

光晕用 `url(#glow)`，进了 Rough.js 的嵌套 `<g>` 之后渐变坐标系跟着变，柔边光晕变成硬边圆盘。
规则：`fill` / `stroke` 带 `url(` 的一律跳过。

### 10. 大椭圆会被拉成几段弦

默认 `curveStepCount: 9` 配抖动，大椭圆会横穿出几道直线。加 `preserveVertices: true` + `curveStepCount: 12`。

### 11. 大椭圆的描边会**整体往里缩**（最容易漏的一个）

`roughness` 对 `ellipse` 不是左右随机抖，而是整条曲线往里缩。实测 184×222 的椭圆：

| roughness | 描边相对真实轮廓 |
|---|---|
| 0 | 完全重合 |
| 1 | 基本贴合 |
| 3 | 横向缩进约 7px |
| 6 | 横向缩进约 14px |

因为填色层是精确路径（r0），描边一缩，中间就露出一圈"内外两条线"。人脸中间会莫名多出一条从太阳穴绕到下巴的深色线。

修法是给抖动加尺寸相关的上限：

```js
const bigCap = span > 150 ? Math.min(2.2, 900 / span) : 99;
const rgn = Math.min(RQ * k * kt, sw * 0.62, span * 0.05, bigCap);
```

184px 的头 → 2.2，600px 的身体 → 1.5。小图元不受影响，而手绘感主要来自它们，观感几乎无损。

## 画面质感（试过但别再用）

### 11.5 `feSpecularLighting` 整组套角色 = 糊

想做"搪胶/塑料质感"，把 `feGaussianBlur(SourceAlpha)` 当高度场再点光源打镜面反射，整组套在 `kaoG/xiG` 上。结果：色块整体被提亮、黑描边冲成灰边、角色像蒙了层雾。

原因：`feSpecularLighting` 假设输入是平滑高度场，角色是几十个独立色块拼的，每个块都在自己的"斜坡"上反光，高光铺满内部而不是只停在边缘。这个滤镜只适合单色小图标，不适合复杂角色。

**替代**：体积感靠「接地阴影 + 背景主光 + 色彩分级」三件套，别指望一个滤镜解决。

### 11.55 加了主光，但光源方向和背景里的太阳打架

给全片加了一层"左上角主光光晕"后，草地白天的太阳在**右上**——同一画面两个光源，观众说不出哪里怪，但就是假。

修法：每个背景声明 `BG.xxx.light = { x, y }`，`ATMO.key` 按当前背景移到对应位置。**新增背景必须同时写 `.light` 和 `.prof`**。

同理，夜间的大气透视是"向天空色靠拢"（更亮更蓝），不是"更暗"——照搬白天的"远山变淡"会让夜山浮起来。

### 11.6 加了镜头缩放后，角色脚会掉出画面

镜头按段做 3–7% 缩放（`CAMERA`），坐标 (960,540) 为心。原来 `feet: 1040/1060` 的角色放大 6% 后脚底到了 1091 > 1080，直接裁掉。

规则：**`feet` 不要超过 1020**。加了新场景先按 `540 + (feet-540) * maxFrom ≤ 1070` 验一遍。

## 配音

### 12. 变调倍数会被放大

EdgeTTS 出的是 **24kHz** mp3。直接 `asetrate=48000` 之类会把采样率也一起改，时间轴整体错位。
正确顺序：`aresample=44100` → `asetrate=44100*倍数` → `atempo=1/倍数` 拉回时长。

### 13. `atempo` 只能吃 0.5–2.0

需要 1.6 倍以上的变调时，串联两个 `atempo`。变调 0.4878（往低走）也要拆成 `atempo=0.5,atempo=0.97561`。

### 14. edge-tts 尾巴会留一段静音

统一裁掉 60–80ms（`areverse,atrim=start=0.06,areverse`），否则每段之间都拖一拍，整片节奏会松。

## 字幕与排版

### 15. SVG `<text>` 不会自动换行

中文段落必须自己折。`build.py` 的 `split_subs` 按「句 → 逗号 → 硬折行」三层切，每行 ≤21 字、最多两行。
手写一整段当字幕，会直接顶出画面（第一次跑出来就是一整行横贯全屏）。

### 16. 气泡宽度必须按字数算

固定宽度（比如"超过 16 字就用 1180"）会让 13 个字的气泡装不下 13 个字。
`bw = clamp(字数*48 + 140, 520, 1280)`。

### 17. 字幕区是禁区

字幕固定占 900–1030，`card` 底边不能超过 880，`show` 的大标题要上移到 `cy+340`。第一次跑出来大标题和字幕叠在一起，看起来像两行字幕。

### 18. 浅色背景上的浅色面板要垫投影 / 描边

`room` 这类暖色室内背景是浅米黄，`card` 也是奶油色，两者贴一起边界会糊成一片。卡片底下垫一层 `fill=INK, opacity=0.16`、偏移 (16,18) 的 `<rect>` 投影，边界立刻立起来。深色背景（草地夜、storm）不需要。

同理，`show` 的标注文字用 `CREAM` 填充 + `INK` 描边（`paint-order="stroke fill"`），这样在深色雷雨云上也读得清。**注意**：预览帧截在标注/字幕淡入的中间态（`opacity≈0.25`）时会显得发灰发淡，这是正常的过场，别误判成对比度 bug——要在段落稳定期（进度 >0.5）再截图判断。

## 音频工程

### 19. 段落化配乐比一条循环好听得多

按分镜给不同织体（`spark` / `soft` / `piano` / `full` / `outro`），配乐跟着画面起伏。一条循环到底会有明显的"背景在放歌"感。

### 20. 铺底要微失谐

单频正弦听着像电子琴。三路 `freq × 1.002 / 0.998` 叠一起才有合唱厚度。

### 21. 母线别裸归一化

`tanh` 软限幅 + 12ms 立体声展宽 + 峰值 -1dB，比直接 `x/max(x)` 干净得多。

## 工程

### 21.5 ffmpeg「写文件」在某些沙箱里被拖慢 30 秒

如果整套流程跑在受限沙箱里（比如 AI agent 的 Bash 工具），`ffmpeg -i x.wav -t 1 out.wav` 可能要 30s+，而 `-f null -` 却 0.01s。**不是 ffmpeg 或磁盘的问题**：同一个命令在普通终端里 168ms。

后果是混音/编码阶段看起来是瓶颈（实测被放大 3–4 倍），容易误判优化方向。核对办法：把同一条命令放到普通终端跑一遍；或在允许时用非沙箱方式执行。Chrome 截图不受此影响，所以渲染速度的测量是准的。

### 22. numpy 不一定在默认 python3 里

macOS 上 `python3` 可能指向没装 numpy 的解释器。先 `python3 -c "import numpy, edge_tts"` 验一下，缺了换个解释器，别在脚本里硬编码路径。

### 23. 时长靠片段数量控制，不靠语速

想从 3 分钟拉到 4 分半，加 5–6 个片段（新知识点/反应镜头），不要调慢语速——语速一慢，孩子反而走神。

### 24. 字幕越说越晚：别按字数分摊

**症状**：一段 11 秒的旁白，字幕到第二句以后明显比语音慢，越往后差得越多；最后一句字幕在语音结束后还挂着。

**两个叠加原因**：
1. 整段一次性合成，只能按字数比例猜每句在哪儿。TTS 的语速和句间停顿并不均匀，猜出来的边界必然漂——实测 11 秒能漂 1.2 秒。
2. 分摊基数是整段 wav 的时长，而 wav 首尾自带静音（edge-tts 句尾常留 0.8–1.3s）。把静音也算进"说话时间"，越靠后的句子分到的时间越靠后。

**改法**：逐句合成。每句单独出音频、量出真实时长，再按 `句长 + 0.12s` 拼成整段，同时记下每句的起点偏移（`__chunks`）。字幕时间点直接取「LEAD + 该句偏移 + 句内分页偏移」，不再估。

**自检**：`build.py script.json --check-align`。它会做结构检查（语音溢出段尾 / 字幕越界 / 重叠）和音轨实测（静音检测比对真实起点），偏差 > 0.35s 就报段号。

### 25. 长句切两行别用「定长切片」

`[c[i:i+21] for i in range(0, len(c), 21)][:2]` 这种写法，遇到 43 字的句子会切成 21+21，**最后一个字直接丢掉**，而且断点经常落在词中间（"做/的"）。

正确做法：先按标点找切点（离中点最近的 `，、：；`），宽度略超两三个字可以接受；实在没标点才退回中点。切完核对 `"".join(lines) == 原文`。

## 22. 渲染引擎选型：Chrome 截图 vs resvg（2026-11 实测）

**结论：本项目的画面不要换 resvg / 纯 SVG 光栅化器，更慢，不是更快。**

| 方案 | 1920×1080 单帧 | 说明 |
|---|---|---|
| Chrome `Page.captureScreenshot` | **35–50ms** | 现有方案，元素多也一样快 |
| `@resvg/resvg-js` | **1600–3700ms** | 同一张 222KB、数千元素的 SVG，慢 40 倍 |

原因：画面是「一个常驻页面反复改 DOM」，Chrome 只重绘变化的部分；resvg 每次都要把
整棵 SVG 树重新解析、重新光栅化（CPU）。元素越多、渐变越多，差距越大。

另外两点：

- **resvg 会 panic 直接杀进程**（`geom.rs: unwrap None`），Rust panic 无法被 JS `try/catch` 接住。
  跑 7000 帧的流水线，只要有一帧踩到就整批废掉。
- CSS `filter: blur()` 被 resvg 静默忽略（本项目用它做投影/光晕），阴影会变硬边。
  换成 SVG `feGaussianBlur` 能兼容，但速度只会更差。

**真正影响出片速度的是内存，不是引擎。** 实测同一台机器：
用户自己开着 53 个 Chrome 进程、可用内存 139MB 时，渲染掉到 3.6 帧/秒且 Chrome 频繁崩溃；
内存宽裕时 3 进程稳定 27 帧/秒。要快就先把内存腾出来，或者 `--jobs 2`。

关于 Obscura（Rust 无头浏览器，30MB）：它的定位是**网页抓取**——HTML/CSS/JS 和执行速度，
不是「几千个矢量元素的重复光栅化」。SVG 渐变、`clipPath`、滤镜的保真度未验证，
不建议拿 4 分钟 × 30fps 的成片流水线去赌。

### 提速实测（同一台机器，1920×1080，单帧 ms）

| 改动 | 结果 | 判断 |
|---|---|---|
| 现状：shell + `--disable-gpu` | 49.1 ms | 基准 |
| **去掉 `--disable-gpu`（已改为默认）** | **41.7 ms** | **+18%，白拿** |
| 新 headless + GPU / angle=metal | 41.8 / 42.7 ms | 与上面持平，不必换模式 |
| JPEG q95 → q88 | 48.9 ms | 无感（编码不是瓶颈） |
| `optimizeForSpeed: true` | 48.9 ms | 无感 |
| `fromSurface: false` | 350 ms | **慢 7 倍，禁用** |

单帧耗时构成：**截图（光栅化）49.5ms ｜ JS+DOM 仅 0.8ms**。
所以引擎再怎么优化 DOM 都没用，瓶颈完全在光栅化。

内存的影响远大于并发：

| 状态 | 吞吐 |
|---|---|
| 可用内存 139MB（用户开着 53 个 Chrome） | 3.6 帧/秒，频繁崩 |
| 可用内存 5GB | 24 帧/秒（单进程） |
| 可用内存 5GB + 3 进程 | 27 帧/秒 |

**结论：并发从 1 加到 3 只多 12%，但内存不够会直接掉到 1/7。**
`--jobs 2~3` 足够，别为了并发把内存吃穿。无 GPU 的容器里用 `CHROME_NO_GPU=1` 关回去。
